## Behaviour changes for what's running now

- `branch_promote` is refused when the branch is behind main (`merge_conflicts`,
  `merge_stale`) unless `allow_stale: true` (D7: kind 1 rebases first, decided 5 Nov).
- A promoted agent's EPISODIC read now also shows the old agent's episodes and an origin
  record. A new branch's EPISODIC holds an origin record.
- Query answers have `metadata.point`; refusals have `code` (added fields).

## Rolling

`p2-rollout.sh` (session scratchpad): backup of the leader's data, then one pod at a time,
followers first, leader last. No schema version change. Expect one election when the leader
restarts. Only the leader reports Ready, by design.

**Followers first matters:** an older node can't read the new record types (`TableAddColumns`,
`TableAppendOnly`, `TablePurge`), so a new leader must not write them to an old follower.

## Undo is limited

Back to `adb:2026-11-05-b7` works only until a new record type is written: `create_table`
with `append_only`, `add_columns`, `append_only`, `purge`, or any `branch_merge` or
`merge_revert` (which write `adb_merges`). After that, the older image can't replay its log, and
undo means restoring the backup and losing writes made since.

**Hold window:** after the roll, a few hours with steady memory, with no `branch_merge`,
`merge_revert`, `append_only`, `add_columns` or `purge` on vc-dev, so undo stays open. Then
re-baseline RSS and report. Sequence: FlowR rolls first, so the two changes can be told apart.
