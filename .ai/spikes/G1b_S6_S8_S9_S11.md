## S6 — object-storage writes vs WAL flush interval (option A, `id` index only)

200 puts/s × 5 rows (768-dim), 60 s, `durable_write(false)`, WAL buffer cap raised to
512 MiB so size doesn't trigger flushes first.

| WAL flush interval | Puts/s reached | Put p50 / p99 | Writes/s to object storage |
|---|---|---|---|
| 1 s | 200 | 0.16 / 0.33 ms | 2.9 |
| 10 s | 200 | 0.13 / 0.76 ms | **0.9** |
| 30 s | 200 | 0.14 / 0.70 ms | **0.8** |

The ~0.8/s floor is memtable → generation flushes (20k-row memtable ≈ one every 20 s
at this load), not the WAL. A bigger memtable lowers it further. At 0.8/s per busy
partition, one bucket's 750 req/s covers several hundred busy partitions' writes (reads
and opens share the same budget — see S7). **Setting: WAL flush 30 s** (the Raft log is
the WAL; a lost MemWAL tail only lengthens replay).

## S8 — vector index at partition scale

Data: unit vectors around 256 clusters × 32 sub-clusters (offsets scaled by
1/√dim), 100 held-out queries, exact cosine top-10 as ground truth. Local disk,
warm, 12 cores. `refine` = re-rank that many × k candidates with the raw vectors.

**Brute force (no index)**

| Rows | 768-dim p50 | 1536-dim p50 |
|---|---|---|
| 10k | 23 ms | 132 ms |
| 50k | 146 ms | 474 ms |

→ Brute force meets the 25 ms recall budget only up to **~10k vectors (768-dim)**;
§7's "~50k" threshold is too high. (In the memtable — RAM, no I/O — it's cheaper.)

**Indexes — build time and best settings**

| Index | 50k × 768 | 50k × 1536 | 500k × 768 | 500k × 1536 |
|---|---|---|---|---|
| **IVF_RQ** (1 bit) build | **4.6 s** | **9.9 s** | **40 s** | **65 s** |
| recall@10, nprobes 20 + refine 5 | 0.976 | 0.967 | 0.971 | 0.982 |
| recall@10, nprobes 50 + refine 10 | 0.998 | 0.996 | 1.000 | 1.000 |
| p50 at refine 10 | 5.1 ms | 8.2 ms | 6.4 ms | 13.4 ms |
| **IVF_HNSW_SQ** build | 6.4 s | 9.7 s | 63 s | 103 s |
| recall@10 (best) | 0.982 | 0.983 | 0.964 | 0.959 |
| **IVF_PQ** build | 49 s | 100 s | 120 s | 221 s |
| recall@10, nprobes 50 + refine 10 | 0.950 | 0.958 | 1.000 | 0.998 |

- **IVF_RQ needs `refine`** — without re-ranking recall is 0.42–0.77; with
  `refine 5–10` it reaches 0.97–1.00 for a few ms more.
- IVF_HNSW_SQ is good without re-ranking but tops out below 0.96–0.98 here and builds
  slower; IVF_PQ is 3–5× slower to build than RQ for no recall gain.
- **Rebuild < 60 s:** met at 500k × 768 (40 s); 500k × 1536 takes 65 s on 12 cores —
  borderline. Partitions that large need either more cores for the build or
  incremental index updates instead of full rebuilds.
- These latencies are local-disk. On object storage add the S4 numbers (~100 ms
  p50) unless the index and refine vectors are in the hot-tier cache.
- `nprobes` 10 vs 20 gave identical results without refine — Lance appears to apply a
  minimum probe count; not investigated further.

## S9 — f16 embeddings in the log

Exact top-10 over vectors and queries rounded to f16 and back, against the f32 truth:

| | 10k | 50k | 500k |
|---|---|---|---|
| 768-dim | 0.999 | 1.000 | 0.998 |
| 1536-dim | 0.999 | 1.000 | 0.995 |

Recall drop ≤ 0.5 % (target < 0.5 %; 500k × 1536 sits exactly at it). Even on the
first, degenerate data set (near-uniform, where neighbours are hardest to separate) it
was 0.998–1.000. **Keep f16 in the log**; tables keep f32 (MemWAL's HNSW needs f32
anyway, S5).

## S11 — is FORGET physical?

Scope `forget-me` written to the base table (500 rows, with BTree, FTS and IVF_FLAT
indexes) and through MemWAL (300 rows flushed to a generation, 100 left in the WAL).
After each step every file was byte-scanned for the vector bytes and the marker text.

| Location | after DELETE + tombstones | + `compact_files` + `optimize_indices` | + `cleanup_old_versions(0)` |
|---|---|---|---|
| Base data files | present | present (old files) | **gone** |
| Index files | present | present (old files) | **gone** |
| MemWAL WAL files | present (400 rows) | present | **present** |
| MemWAL generations | present (+ new generation on close) | present | **present** |

- **Base table: forget is physical** once all three steps run. Old index files keep
  the vectors until the cleanup, so cleanup is part of forget, not optional.
- **MemWAL: Lance never deletes WAL files or generations** (no GC code; not covered by
  `cleanup_old_versions`). Tombstones hide rows from reads but the bytes stay,
  readable. Closing the writer even flushed the forgotten rows into a new generation.
- **What ADB must build (in `adb-store`):** after folding generations into the base
  table (`merge_insert(..).mark_sstables_as_compacted(..)`), delete the compacted
  generation folders and the WAL files below the shard's `replay_after_wal_entry_position`.
  FORGET = tombstones → generation compaction → MemWAL GC → base delete + compact +
  `cleanup_old_versions`. The forget SLA is the sum of those cadences.
- Limitation: Lance compresses strings in base data files, so the marker text was
  not visible there even before deletion; the vector bytes are the evidence for the
  base table (rows are deleted whole).
